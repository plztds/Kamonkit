## 1. ภาพรวมธุรกิจ (Business Overview)

### ลักษณะธุรกิจ
ร้านกมลกิจยานยนต์เป็นร้านค้าปลีก-บริการรถจักรยานยนต์ ครอบคลุม 5 สายงานหลัก:
- จำหน่ายรถจักรยานยนต์มือหนึ่งและมือสอง
- รับซ่อมบำรุงรถจักรยานยนต์ทุกยี่ห้อ
- จำหน่ายอะไหล่รถจักรยานยนต์
- ให้บริการสินเชื่อผ่อนชำระรถจักรยานยนต์ (In-house Financing)
- ให้บริการทำ พ.ร.บ. และต่อภาษีรถประจำปี

### ผู้ใช้ระบบ (4 Roles)

| Role | หน้าที่หลัก | Platform หลัก |
|------|-----------|--------------|
| **เจ้าของร้าน (Owner/Admin)** | ดูรายงานสรุป ตรวจสอบภาพรวมธุรกิจ จัดการข้อมูลหลัก อนุมัติรายการพิเศษ | Mobile App |
| **เสมียน (Clerk)** | บันทึกธุรกรรมทั้งหมด จัดการเงินสดประจำวัน มอบหมายงานติดตามหนี้ | Web App (PC) |
| **ช่างซ่อม (Technician)** | บันทึกงานซ่อม เบิกอะไหล่ | Web App (PC) + Barcode Scanner |
| **พนง.ติดตามหนี้ (Collector)** | ออกพื้นที่ติดตามหนี้ เก็บเงินหน้างาน | Mobile App |

## 2. ข้อมูลหลัก (Master Data)

### 2.1 รถจักรยานยนต์ (Vehicle)

**REQ-VEH-001: บันทึกข้อมูลรถ**
- ระบบต้องบันทึกข้อมูลรถจักรยานยนต์ได้ ประกอบด้วย: ยี่ห้อ (brand), รุ่น (model), ปี (year), สี (color), เลขตัวถัง (chassis_no), เลขเครื่อง (engine_no), ทะเบียน (license_plate), สภาพ (new/used), ราคาทุน (cost_price), ราคาขาย (selling_price)
- เลขตัวถังและเลขเครื่องต้องไม่ซ้ำกัน (unique) ในระบบ

**REQ-VEH-002: สถานะรถ**
- รถต้องมีสถานะเป็นหนึ่งใน: `in_stock` (ในสต็อก), `sold` (ขายแล้ว), `reserved` (จอง)
- รถที่ `sold` แล้วจะเปลี่ยนกลับเป็น `in_stock` ไม่ได้ ยกเว้น Admin override (กรณียกเลิกสัญญา/ยึดรถคืน)

**REQ-VEH-003: ค้นหารถ**
- ค้นหาได้ด้วย: ทะเบียน, เลขตัวถัง, เลขเครื่อง, ยี่ห้อ, รุ่น, สถานะ

**REQ-VEH-004: เชื่อมโยงรถกับลูกค้า**
- เมื่อขายรถ ระบบต้องบันทึก customer_id ไว้กับรถ เพื่อทราบว่ารถเป็นของลูกค้าใด

**REQ-VEH-005: สภาพรถ**
- ต้องระบุว่ารถเป็น `new` (มือหนึ่ง) หรือ `used` (มือสอง) ตั้งแต่ตอนบันทึก
- สภาพรถจะเปลี่ยนแปลงภายหลังไม่ได้

**REQ-VEH-006: ราคารถ**
- ราคาทุน (cost_price) และราคาขาย (selling_price) ต้องเป็นตัวเลขที่มากกว่า 0
- ราคาขายต้องมากกว่าหรือเท่ากับราคาทุน (ระบบเตือนแต่ไม่บล็อก หากตั้งราคาขายต่ำกว่าทุน)

**REQ-VEH-007: Soft Delete**
- รถที่ถูกลบจะไม่ลบจริง ใช้วิธี Soft Delete เท่านั้น เพื่อรักษาข้อมูลอ้างอิงในสัญญา

### 2.2 ลูกค้า (Customer)

**REQ-CUS-001: บันทึกข้อมูลลูกค้า**
- ข้อมูลลูกค้าประกอบด้วย: เลขบัตรประชาชน (citizen_id), ชื่อ-นามสกุล, เบอร์โทร (phone), เบอร์โทรสำรอง (phone2), ที่อยู่ (address, ตำบล, อำเภอ, จังหวัด, รหัสไปรษณีย์), หมายเหตุ
- ชื่อ, นามสกุล, เบอร์โทร เป็นข้อมูลบังคับ
- เลขบัตรประชาชนต้องไม่ซ้ำกัน (ถ้ากรอก)

**REQ-CUS-002: ป้องกันข้อมูลลูกค้าซ้ำ**
- เมื่อสร้างลูกค้าใหม่ ระบบต้องค้นหาด้วยเบอร์โทรก่อน
- ถ้าพบข้อมูลที่คล้ายกัน (เบอร์โทรตรง หรือชื่อใกล้เคียง) ต้องแจ้งเตือนผู้ใช้
- รองรับการ Merge ลูกค้าที่ซ้ำกัน (Admin only)

**REQ-CUS-003: ค้นหาลูกค้า**
- ค้นหาได้ด้วย: ชื่อ-นามสกุล, เบอร์โทร, เลขบัตรประชาชน

**REQ-CUS-004: ประวัติลูกค้า**
- ระบบต้องแสดงประวัติลูกค้าได้ ประกอบด้วย: รถที่ซื้อ, สัญญาทั้งหมด, ประวัติชำระค่างวด, ประวัติงานซ่อม, ประวัติ พ.ร.บ./ภาษี

**REQ-CUS-005: ข้อมูลส่วนบุคคล (PII)**
- เลขบัตรประชาชนและเบอร์โทรเป็นข้อมูลส่วนบุคคล ต้อง mask ใน Log และ Response ที่ไม่จำเป็น
- เลขบัตร → `1234-XXXX-XXXX-5678`, เบอร์โทร → `08X-XXX-1234`

**REQ-CUS-006: Soft Delete**
- ลูกค้าที่มีสัญญาหรือประวัติธุรกรรมจะลบไม่ได้ ใช้ Soft Delete เท่านั้น

**REQ-CUS-007: เลขบัตรประชาชน**
- ต้องเป็นตัวเลข 13 หลัก (ถ้ากรอก)
- ใช้ตรวจสอบ checksum ตามอัลกอริทึมมาตรฐาน

### 2.3 ผู้ค้ำประกัน (Guarantor) `[GAP FILL]`

**REQ-GUA-001: บันทึกข้อมูลผู้ค้ำประกัน**
- สัญญาผ่อนชำระสามารถมีผู้ค้ำประกันได้ (ไม่บังคับ)
- ข้อมูลผู้ค้ำประกันประกอบด้วย: ชื่อ-นามสกุล, เลขบัตรประชาชน, เบอร์โทร, ที่อยู่, ความสัมพันธ์กับลูกค้า
- ผู้ค้ำประกัน 1 คนสามารถค้ำประกันได้หลายสัญญา

**REQ-GUA-002: เชื่อมโยงกับสัญญา**
- ระบบต้องบันทึกความสัมพันธ์ระหว่างผู้ค้ำประกันกับสัญญาผ่อนชำระ
- Collector สามารถดูข้อมูลผู้ค้ำประกันได้ เมื่อต้องติดตามหนี้

**REQ-GUA-003: ข้อมูลผู้ค้ำประกันในกรณีติดตามหนี้**
- เมื่อลูกค้าค้างชำระเกินกำหนด ระบบต้องแสดงข้อมูลผู้ค้ำประกัน (ชื่อ, เบอร์โทร, ที่อยู่) ให้ Collector เห็น
- Collector ไม่มีสิทธิ์แก้ไขข้อมูลผู้ค้ำประกัน

### 2.4 อะไหล่ (Parts)

**REQ-PRT-001: บันทึกข้อมูลอะไหล่**
- ข้อมูลอะไหล่ประกอบด้วย: รหัสอะไหล่ (part_code), barcode, ชื่อ, คำอธิบาย, หน่วยนับ (unit), ราคาทุน (cost_price), ราคาขาย (selling_price), จำนวนคงเหลือ (quantity_in_stock), ระดับสต็อกขั้นต่ำ (min_stock_level), ตำแหน่งจัดเก็บ (location), หมวดหมู่ (category)
- รหัสอะไหล่ต้องไม่ซ้ำกัน (unique)

**REQ-PRT-002: หมวดหมู่อะไหล่**
- อะไหล่ต้องจัดอยู่ในหมวดหมู่ (category) เช่น ผ้าเบรค, น้ำมัน, ไฟฟ้า, ยาง เป็นต้น
- หมวดหมู่สร้างได้อิสระ ชื่อต้องไม่ซ้ำกัน

**REQ-PRT-003: Barcode**
- รองรับ barcode จากผู้ผลิต + internal part code (ไม่ซ้ำกัน)
- barcode อาจซ้ำกัน (กรณีสินค้าจาก supplier หลายรายใช้ barcode เดียวกัน) — ระบบต้องรองรับการแก้ไขปัญหาความซ้ำซ้อน

**REQ-PRT-004: ราคาอะไหล่**
- ราคาทุนและราคาขายต้องเป็นตัวเลขที่มากกว่า 0
- ราคาขายต้องมากกว่าราคาทุน (ระบบเตือนแต่ไม่บล็อก)

**REQ-PRT-005: สถานะอะไหล่**
- อะไหล่มีสถานะ active/inactive
- อะไหล่ที่ inactive จะไม่แสดงในรายการเบิก/ขาย แต่ยังอยู่ในฐานข้อมูล

**REQ-PRT-006: หน่วยนับ**
- ต้องระบุหน่วยนับ เช่น ชิ้น, ลิตร, กล่อง, คู่ เป็นต้น
- ค่า default: "ชิ้น"

**REQ-PRT-007: แจ้งเตือนสต็อกต่ำ (Low Stock Alert)**
- เมื่อจำนวนคงเหลือ ≤ ระดับสต็อกขั้นต่ำ (min_stock_level) ระบบต้องแจ้งเตือน
- ระดับสต็อกขั้นต่ำตั้งค่าได้ต่ออะไหล่ ค่า default: 5

## 3. การขายและสัญญาซื้อขาย (Sales & Contract)

### 3.1 ขายเงินสด (Cash Sale)

**REQ-SALE-001: สร้างสัญญาขายเงินสด**
- ระบบต้องรองรับการขายรถเป็นเงินสด
- ต้องเลือกลูกค้า (หรือสร้างใหม่) และเลือกรถจากสต็อก (status = `in_stock`)
- กำหนดราคาขาย (total_price)

**REQ-SALE-002: ผลของการขายเงินสด**
- สถานะรถเปลี่ยนเป็น `sold`
- บันทึก customer_id ไว้กับรถ
- สร้าง Cash Transaction ประเภท `income` หมวด `vehicle_sale`
- ออกใบเสร็จรับเงิน

**REQ-SALE-003: เลขที่สัญญา**
- ทุกสัญญาต้องมีเลขที่สัญญา (contract_number) ที่ไม่ซ้ำกัน
- ระบบสร้างเลขที่สัญญาอัตโนมัติ ในรูปแบบ `KK-{ปี พ.ศ.}-{running number 4 หลัก}` เช่น KK-2569-0042

**REQ-SALE-004: สัญญาต้องบันทึกผู้รับผิดชอบ**
- ทุกสัญญาต้องบันทึก clerk_id ว่าเสมียนคนใดเป็นผู้บันทึก

### 3.2 ผ่อนชำระ (Installment Sale)

**REQ-SALE-010: สร้างสัญญาผ่อนชำระ**
- ระบบต้องรองรับการขายรถแบบผ่อนชำระ (In-house Financing)
- ต้องเลือกลูกค้าและรถจากสต็อก (status = `in_stock`)
- กำหนดเงื่อนไขดังนี้:
  - ราคาขาย (total_price)
  - เงินดาวน์ (down_payment) — ต้อง ≥ 0 และ < ราคาขาย
  - จำนวนงวด (total_installments)
  - อัตราดอกเบี้ย (interest_rate) — optional, ส่วนใหญ่บวกเข้าราคาขายแล้ว
  - วันที่ครบกำหนดในแต่ละเดือน (due_day_of_month) — เช่น ทุกวันที่ 15
  - วันผ่อนผัน (grace_period_days) — default 7 วัน
  - ประเภทค่าปรับ (penalty_type) + อัตราค่าปรับ (penalty_rate)

**REQ-SALE-011: คำนวณยอดผ่อน**
- `finance_amount = total_price - down_payment`
- `installment_amount = finance_amount / total_installments` (ปัดขึ้นเป็นจำนวนเต็ม)
- งวดสุดท้ายปรับยอดเพื่อให้ยอดรวมตรงกับ finance_amount (ไม่มีเศษค้าง)

**REQ-SALE-012: สร้างงวดอัตโนมัติ**
- ระบบต้องสร้างรายการงวด (installment records) ตามจำนวนงวดที่กำหนด
- แต่ละงวดมี: เลขงวด, วันครบกำหนด (due_date), จำนวนเงิน, สถานะ (pending)
- วันครบกำหนดคำนวณจาก due_day_of_month โดยเริ่มจากเดือนถัดไปหลังวันทำสัญญา

**REQ-SALE-013: การจัดการเล่มทะเบียน**
- กรณีผ่อนชำระ: เล่มทะเบียนเก็บไว้ที่ร้าน (registration_status = `held_by_shop`) เป็นหลักประกัน
- เมื่อลูกค้าผ่อนครบ: เล่มทะเบียนส่งคืนลูกค้า (registration_status = `returned_to_customer`)
- กรณีขายเงินสด: ไม่ต้องเก็บเล่มทะเบียน

**REQ-SALE-014: ผลของการสร้างสัญญาผ่อนชำระ**
- สถานะรถเปลี่ยนเป็น `sold`
- บันทึก customer_id ไว้กับรถ
- Registration status → `held_by_shop`
- บันทึก Cash Transaction สำหรับเงินดาวน์ (ถ้ามี) ประเภท `income` หมวด `vehicle_sale`
- ทั้งหมดต้องเกิดภายใน transaction เดียว (atomic) — ถ้าขั้นตอนใดล้มเหลว ต้อง rollback ทั้งหมด

**REQ-SALE-015: ตรวจสอบก่อนสร้างสัญญา**
- รถต้องมีสถานะ `in_stock` — ถ้าไม่ใช่ ปฏิเสธทันที
- ลูกค้าต้องมีข้อมูลครบ (ชื่อ, เบอร์โทร)
- เงินดาวน์ต้อง ≥ 0 และ < ราคาขาย
- จำนวนงวดต้อง > 0

**REQ-SALE-016: สถานะสัญญา**
- สัญญามีสถานะ: `active` (กำลังผ่อน), `completed` (ผ่อนครบ), `defaulted` (ผิดนัด/ยึดรถ)
- สัญญาเปลี่ยนเป็น `completed` อัตโนมัติเมื่อผ่อนครบทุกงวด
- สัญญาเปลี่ยนเป็น `defaulted` ได้เฉพาะ Admin

**REQ-SALE-017: ค่าปรับที่ตั้งได้ต่อสัญญา**
- แต่ละสัญญาสามารถตั้งค่าประเภทค่าปรับและอัตราค่าปรับได้แตกต่างกัน
- ประเภทค่าปรับมี 3 แบบ (ดู REQ-PEN-001)
- ค่า default: fixed 100 บาท/งวด

**REQ-SALE-018: เงินดาวน์**
- เงินดาวน์ต้องรับเป็นเงินสด ณ วันทำสัญญา
- ระบบต้องบันทึกเงินดาวน์เข้า Cash Transaction อัตโนมัติ

**REQ-SALE-019: วันผ่อนผันที่ตั้งได้ต่อสัญญา**
- จำนวนวันผ่อนผัน (grace_period_days) ตั้งค่าได้ต่อสัญญา
- ค่า default: 7 วัน
- หมายความว่า ถ้าครบกำหนดวันที่ 15 แล้วลูกค้ามาจ่ายภายในวันที่ 22 จะยังไม่คิดค่าปรับ

**REQ-SALE-020: ข้อจำกัดการแก้ไขสัญญา**
- สัญญาที่ `active` แก้ไขข้อมูลหลักได้เฉพาะ Admin (เช่น เปลี่ยน due_day_of_month, penalty_rate)
- สัญญาที่ `completed` หรือ `defaulted` แก้ไขไม่ได้
- การชำระเงินที่บันทึกแล้วจะแก้ไขหรือลบไม่ได้ — ต้องใช้ reversal entry เท่านั้น

### 3.3 กฎทั่วไป (General Sales Rules)

**REQ-SALE-030: จองรถ (Vehicle Reservation)** `[GAP FILL]`
- รถสามารถ "จอง" ได้ (status = `reserved`) โดยเสมียน
- รถที่จองแล้วจะไม่แสดงในรายการรถพร้อมขาย
- การจองมีระยะเวลา ถ้าไม่มาทำสัญญาภายในระยะเวลาที่กำหนด ระบบเปลี่ยนสถานะกลับเป็น `in_stock`

**REQ-SALE-031: 1 รถ = 1 สัญญา**
- รถ 1 คันมีได้แค่ 1 สัญญาที่ active
- จะสร้างสัญญาใหม่ให้รถที่มีสัญญา active อยู่ไม่ได้

**REQ-SALE-032: ใบเสร็จ Running Number**
- ใบเสร็จต้องมีเลขที่ running number ที่ไม่ซ้ำกัน
- ทุกการรับเงินต้องพิมพ์ใบเสร็จ (บังคับ) เพื่อป้องกันการรับเงินแล้วไม่บันทึก

**REQ-SALE-033: Trade-in (รถแลกเปลี่ยน)** `[GAP FILL]`
- รองรับกรณีลูกค้านำรถเก่ามาแลกเป็นส่วนลด
- ระบบต้องบันทึกรถที่รับแลก (เข้าสต็อกเป็นรถมือสอง) และมูลค่าที่ตีราคา
- มูลค่า trade-in หักจากราคาขาย ก่อนคำนวณยอดผ่อน (ถ้าผ่อน)

### 3.4 ประกันรถหาย (Theft Insurance) `[NEW]`

**REQ-INS-001: ลักษณะการประกัน**
- ร้านจัดการประกันรถหายเอง (Self-insurance) ไม่ใช่บริษัทประกัน
- เงินค่าประกันเก็บเข้า "กองกลางประกันรถหาย" (Theft Insurance Fund)
- วัตถุประสงค์: คุ้มครองกรณีรถจักรยานยนต์ที่ลูกค้าซื้อผ่อนถูกขโมย

**REQ-INS-002: เงื่อนไขบังคับประกัน**
- บังคับเฉพาะ **รถใหม่ (condition = new) ที่ซื้อแบบผ่อนชำระ** เท่านั้น
- รถมือสอง (used) ไม่บังคับ แต่สามารถเลือกซื้อประกันได้ (optional)
- ขายเงินสดไม่ต้องมีประกันรถหาย

**REQ-INS-003: ค่าประกัน**
- ค่าประกันเป็นจำนวนเงินคงที่ต่องวด (เช่น 50 บาท/งวด หรือ 100 บาท/งวด)
- จำนวนเงินตั้งค่าได้ต่อสัญญา ณ เวลาสร้างสัญญา
- ค่าประกันเก็บพร้อมกับค่างวดในแต่ละงวด (รวมอยู่ในยอดที่ลูกค้าต้องจ่ายแต่ละเดือน)
- ค่าประกันต้องแสดงแยกบรรทัดจากค่างวดปกติ ทั้งในระบบและในใบเสร็จ

**REQ-INS-004: การเก็บเงินค่าประกัน**
- เมื่อลูกค้าจ่ายค่างวด ระบบบันทึกค่าประกันเข้า Cash Transaction แยกจากค่างวด
- หมวดหมู่ Cash Transaction: `theft_insurance`
- ยอดกองกลางต้องสะสมและติดตามได้

**REQ-INS-005: กรณีรถหาย — ลูกค้าหยุดผ่อน**
- เมื่อรถถูกขโมย (พิสูจน์ได้): ลูกค้าหยุดผ่อนชำระทันที
- งวดที่เหลือทั้งหมดจะถูกยกเลิก (cancel remaining installments)
- สัญญาเปลี่ยนสถานะเป็น `closed_theft` (ปิดเพราะรถหาย)
- ลูกค้าไม่ต้องรับผิดชอบยอดคงค้าง
- ร้านรับความเสียหาย (เงินจากกองกลาง)

**REQ-INS-006: หลักฐานรถหาย**
- ต้องมีใบแจ้งความ (Police Report) เป็นหลักฐาน
- Admin เป็นผู้อนุมัติการปิดสัญญาเนื่องจากรถหาย
- ระบบต้องบันทึก: วันที่รถหาย, เลขที่ใบแจ้งความ, วันที่อนุมัติ, ผู้อนุมัติ

**REQ-INS-007: กองกลางประกันรถหาย (Theft Insurance Fund)**
- ระบบต้องติดตามยอดเงินกองกลางได้แบบ real-time
- ยอดกองกลาง = ผลรวมค่าประกันที่เก็บได้ - ผลรวมความเสียหายจากรถหาย
- แสดงในรายงานให้ Admin/Owner ดูได้

**REQ-INS-008: ค่าประกันเมื่อผ่อนครบ**
- เมื่อลูกค้าผ่อนครบทุกงวด ค่าประกันที่จ่ายไปแล้วจะไม่คืน
- ค่าประกันเป็น non-refundable

**REQ-INS-009: ประกันคุ้มครองเฉพาะกรณีรถหาย**
- คุ้มครองเฉพาะ "ถูกขโมย" เท่านั้น
- ไม่คุ้มครองกรณี: อุบัติเหตุ, ไฟไหม้, น้ำท่วม, สูญหายจากความประมาท

**REQ-INS-010: ค่าประกันไม่นับรวมค่างวด**
- ค่าประกันรถหายเป็นยอดแยกจากค่างวด — ไม่นำมาคำนวณค่าปรับล่าช้า
- ค่าปรับล่าช้าคิดจากค่างวดปกติเท่านั้น

**REQ-INS-011: การจ่ายค่าประกัน**
- ลูกค้าต้องจ่ายค่าประกันพร้อมค่างวด
- ถ้าลูกค้าจ่ายไม่ครบ (partial payment) ให้หักค่างวดก่อน แล้วค่าประกันทีหลัง
- ค่าประกันค้างจ่ายไม่มีค่าปรับ แต่ต้องจ่ายให้ครบก่อนปิดสัญญา

**REQ-INS-012: ยกเว้นประกันรถหาย**
- Admin สามารถยกเว้นการบังคับประกันรถหายได้เป็นกรณีๆ ไป
- ต้องบันทึกเหตุผลการยกเว้นและผู้อนุมัติ

**REQ-INS-013: รายงานกองกลาง**
- ระบบต้องมีรายงานกองกลางประกันรถหาย ประกอบด้วย:
  - ยอดเงินกองกลางปัจจุบัน
  - รายการเงินเข้า (ค่าประกันที่เก็บจากลูกค้า) แยกตามสัญญา
  - รายการเงินออก (ความเสียหายจากรถหาย) แยกตามกรณี
  - สถิติ: จำนวนสัญญาที่มีประกัน, จำนวนเคสรถหาย, อัตราส่วนเคลม

### 3.5 ถ่ายรูปลูกค้า (Customer Photos) `[NEW]`

**REQ-PHO-001: ถ่ายรูปลูกค้าตอนขาย**
- เมื่อขายรถ (ทั้งเงินสดและผ่อน) ต้องถ่ายรูปลูกค้าพร้อมรถเก็บไว้
- วัตถุประสงค์: เก็บเป็นหลักฐานยืนยันตัวตน และใช้ในการติดตามหนี้ (กรณีผ่อน)

**REQ-PHO-002: รูปที่ต้องถ่าย**
- รูปลูกค้า (หน้าตรง)
- รูปลูกค้ากับรถ (เห็นหน้าลูกค้าและรถชัด)
- รูปบัตรประชาชนลูกค้า
- รูปเพิ่มเติม (optional) — เช่น รูปบ้านลูกค้า, รูปผู้ค้ำประกัน

**REQ-PHO-003: เชื่อมโยงรูปกับสัญญา**
- รูปทั้งหมดต้องเชื่อมโยงกับสัญญาซื้อขาย (contract_id)
- ต้องบันทึกประเภทรูป (photo_type): customer_face, customer_with_vehicle, id_card, guarantor, other
- ต้องบันทึกวันเวลาที่ถ่าย

**REQ-PHO-004: การเข้าถึงรูป**
- เสมียน: ดู/อัปโหลดรูปได้ตอนสร้างสัญญา
- Collector: ดูรูปลูกค้าได้ (เพื่อจำหน้าตอนไปตามหนี้) แต่ดาวน์โหลดไม่ได้
- Owner/Admin: ดูรูปได้ทั้งหมด
- ช่าง: ไม่มีสิทธิ์เข้าถึงรูปลูกค้า

**REQ-PHO-005: บังคับถ่ายรูป (กรณีผ่อน)**
- สัญญาผ่อนชำระ: ต้องมีรูปลูกค้าอย่างน้อย 2 รูป (หน้าตรง + กับรถ) จึงจะบันทึกสัญญาได้
- สัญญาเงินสด: แนะนำถ่ายแต่ไม่บังคับ

**REQ-PHO-006: ขนาดและรูปแบบไฟล์**
- รองรับไฟล์ JPEG, PNG
- ขนาดไฟล์สูงสุด: 10 MB ต่อรูป
- ระบบอาจ compress รูปเพื่อประหยัดพื้นที่

**REQ-PHO-007: การจัดเก็บ**
- รูปเก็บใน File Storage (Local หรือ S3-compatible)
- ต้องมี backup รูปไม่ให้สูญหาย
- รูปต้องไม่เข้าถึงได้จาก public URL — ต้อง authenticate ก่อน

**REQ-PHO-008: การลบรูป**
- รูปลูกค้าไม่สามารถลบได้จนกว่าสัญญาจะ completed หรือ defaulted
- หลังสัญญาปิด: Admin ลบได้ตาม Data Retention Policy

**REQ-PHO-009: Privacy**
- รูปลูกค้าเป็นข้อมูลส่วนบุคคล (PII) ต้องจัดการตาม PDPA
- ลูกค้าต้องให้ความยินยอม (consent) ก่อนถ่ายรูป
- ระบบต้องบันทึกว่าลูกค้ายินยอมแล้ว

## 4. ระบบผ่อนชำระ (Installment System)

### 4.1 รับชำระค่างวด (Payment)

**REQ-PAY-001: รับชำระค่างวดที่ร้าน**
- เสมียนค้นหาลูกค้า (ด้วยชื่อ, เบอร์โทร, เลขสัญญา, หรือทะเบียนรถ) เลือกงวดที่ค้าง แล้วบันทึกการชำระ
- ระบบต้องแสดงข้อมูล: ค่างวด, ค่าปรับ (ถ้ามี), ค่าประกันรถหาย (ถ้ามี), ยอดรวมที่ต้องชำระ

**REQ-PAY-002: แสดงค่าปรับแยกจากค่างวด**
- ค่าปรับล่าช้าต้องแสดงแยกบรรทัดจากค่างวดปกติ ทั้งบนหน้าจอและในใบเสร็จ
- ใบเสร็จต้องแสดง: ค่างวด, ค่าปรับ, ค่าประกัน (ถ้ามี), ยอดรวม

**REQ-PAY-003: Partial Payment (จ่ายบางส่วน)**
- รองรับการจ่ายไม่ครบยอดงวด
- เมื่อจ่ายบางส่วน สถานะงวดเปลี่ยนเป็น `partial`
- ยอดคงค้างต้องแสดงให้ลูกค้าและเสมียนเห็น
- ลำดับการจัดสรรเงิน (กรณีจ่ายไม่ครบ): ค่าปรับ → ค่างวด → ค่าประกัน

**REQ-PAY-004: ใบเสร็จ**
- ทุกการรับชำระต้องออกใบเสร็จ (บังคับ)
- ใบเสร็จมี running number (REQ-SALE-032)
- รองรับพิมพ์ทั้ง Thermal Printer (80mm) และ PDF

**REQ-PAY-005: ช่องทางชำระเงิน** `[GAP FILL]`
- รองรับช่องทางชำระเงิน: เงินสด (cash), โอนธนาคาร (bank_transfer), PromptPay
- ทุกช่องทางต้องบันทึกเข้า Cash Transaction เหมือนกัน
- กรณีโอน/PromptPay: ต้องระบุหลักฐาน (เช่น เลขที่อ้างอิง)

**REQ-PAY-006: ปิดสัญญาอัตโนมัติเมื่อผ่อนครบ**
- เมื่องวดสุดท้ายถูกชำระ ระบบต้อง:
  - เปลี่ยนสถานะสัญญาเป็น `completed`
  - เปลี่ยน registration_status เป็น `returned_to_customer`
  - ตรวจสอบค่าประกันรถหายค้างจ่าย — ต้องจ่ายครบก่อนปิดสัญญา

**REQ-PAY-007: จ่ายหลายงวดพร้อมกัน (Multi-installment Payment)** `[GAP FILL]`
- ลูกค้าสามารถจ่ายค่างวดหลายงวดในคราวเดียวได้
- ระบบต้องคำนวณยอดรวม (ค่างวด + ค่าปรับ + ค่าประกัน ของทุกงวดที่เลือก)
- ออกใบเสร็จรวม 1 ใบ

**REQ-PAY-008: จ่ายงวดล่วงหน้า (Advance Payment)** `[GAP FILL]`
- ลูกค้าสามารถจ่ายค่างวดล่วงหน้าได้ (ก่อนถึง due_date)
- งวดที่จ่ายล่วงหน้าไม่มีค่าปรับ

**REQ-PAY-009: จ่ายปิดยอด (Early Payoff)** `[GAP FILL]`
- ลูกค้าสามารถจ่ายปิดยอดทั้งหมดในครั้งเดียวได้
- ยอดปิด = ผลรวมค่างวดคงค้างทั้งหมด + ค่าปรับค้างจ่าย + ค่าประกันค้างจ่าย
- ไม่มีส่วนลดจากการจ่ายปิดยอดก่อนกำหนด (ยกเว้น Admin อนุมัติส่วนลด)

**REQ-PAY-010: บันทึก Cash Transaction อัตโนมัติ**
- ทุกการรับชำระค่างวดต้องสร้าง Cash Transaction ประเภท `income` หมวด `installment` อัตโนมัติ
- ค่าประกันรถหายต้องสร้าง Cash Transaction แยก หมวด `theft_insurance`

### 4.2 ค่าปรับล่าช้า (Late Payment Penalty)

**REQ-PEN-001: ประเภทค่าปรับ**
- ระบบรองรับ 3 ประเภท:
  1. **Fixed** — ค่าปรับคงที่ต่องวดที่ค้าง เช่น 100 บาท/งวด (ไม่สะสมตามวัน)
  2. **Percent Daily** — เปอร์เซ็นต์ต่อวันของยอดค่างวด เช่น 0.1%/วัน
  3. **Percent Monthly** — เปอร์เซ็นต์ต่อเดือนของยอดค่างวด เช่น 3%/เดือน (ปัดขึ้นเป็นเดือน)

**REQ-PEN-002: วันผ่อนผัน (Grace Period)**
- ค่าปรับเริ่มคิดหลังจากเลย due_date + grace_period_days
- ตัวอย่าง: ครบกำหนดวันที่ 15, grace period 7 วัน → เริ่มคิดค่าปรับตั้งแต่วันที่ 23

**REQ-PEN-003: การคำนวณค่าปรับ (Fixed)**
- `penalty_amount = penalty_rate` (จำนวนเงินคงที่)
- ไม่สะสมตามจำนวนวันที่ค้าง

**REQ-PEN-004: การคำนวณค่าปรับ (Percent Daily)**
- `days_chargeable = days_overdue - grace_period_days`
- `penalty_amount = installment_amount × (penalty_rate / 100) × days_chargeable`
- ปัดเป็นจำนวนเต็ม (round)

**REQ-PEN-005: การคำนวณค่าปรับ (Percent Monthly)**
- `months_overdue = CEIL(days_chargeable / 30)`
- `penalty_amount = installment_amount × (penalty_rate / 100) × months_overdue`
- ปัดเป็นจำนวนเต็ม (round)

**REQ-PEN-006: ระบบคำนวณค่าปรับอัตโนมัติ**
- ค่าปรับต้องคำนวณโดยระบบเท่านั้น ผู้ใช้ไม่สามารถแก้ไขค่าปรับด้วยมือ (ยกเว้น REQ-PEN-008)
- Scheduled Job ทำงานทุกวัน เวลา 00:05 เพื่อ:
  - อัปเดตสถานะงวดที่เลยกำหนดเป็น `overdue`
  - คำนวณและบันทึก penalty record

**REQ-PEN-007: บันทึกค่าปรับ**
- ทุก penalty ต้องบันทึกเป็น penalty_record ประกอบด้วย: installment_id, penalty_amount, days_overdue, calculated_at, is_paid, paid_at
- ค่าปรับที่ชำระแล้วต้อง mark เป็น `is_paid = true`

**REQ-PEN-008: ยกเว้น/ลดค่าปรับ (Admin Override)** `[GAP FILL]`
- Admin สามารถยกเว้นหรือลดค่าปรับได้เป็นกรณีๆ ไป
- ต้องบันทึกเหตุผลการยกเว้น/ลด และผู้อนุมัติ
- Audit Log ต้องบันทึก action นี้

**REQ-PEN-009: ค่าปรับไม่ติดลบ**
- ค่าปรับต้อง ≥ 0 เสมอ ไม่มีกรณีที่ค่าปรับเป็นลบ

**REQ-PEN-010: ค่าปรับแสดงในใบเสร็จ**
- ใบเสร็จต้องแสดงค่าปรับแยกบรรทัด ระบุจำนวนวันที่ค้าง และประเภทค่าปรับ

### 4.3 สถานะงวดและสัญญา (Status)

**REQ-STA-001: สถานะงวด (Installment Status)**
- `pending` — ยังไม่ถึงกำหนด หรือถึงกำหนดแล้วแต่ยังอยู่ใน grace period
- `paid` — ชำระครบแล้ว
- `overdue` — เลยกำหนด + grace period แล้วยังไม่ชำระ
- `partial` — ชำระบางส่วน

**REQ-STA-002: เปลี่ยนสถานะงวดอัตโนมัติ**
- `pending` → `overdue`: Scheduled Job ทำงานทุกวัน (เมื่อเลย due_date)
- `pending`/`overdue`/`partial` → `paid`: เมื่อชำระครบ
- `pending`/`overdue` → `partial`: เมื่อชำระบางส่วน

**REQ-STA-003: สถานะสัญญา (Contract Status)**
- `active` — กำลังผ่อนอยู่
- `completed` — ผ่อนครบทุกงวดแล้ว
- `defaulted` — ผิดนัด/ยึดรถ (Admin เปลี่ยนเท่านั้น)
- `closed_theft` — ปิดเพราะรถหาย (กรณีมีประกัน — REQ-INS-005)

**REQ-STA-004: เปลี่ยนสถานะสัญญา**
- `active` → `completed`: อัตโนมัติเมื่อผ่อนครบ
- `active` → `defaulted`: Admin เปลี่ยนเท่านั้น
- `active` → `closed_theft`: Admin เปลี่ยนเท่านั้น (ต้องมีหลักฐาน REQ-INS-006)
- สถานะ `completed`, `defaulted`, `closed_theft` เป็น terminal state — เปลี่ยนกลับไม่ได้

**REQ-STA-005: คืนเล่มทะเบียนเมื่อผ่อนครบ**
- เมื่อสัญญา completed → เล่มทะเบียนเปลี่ยนเป็น `returned_to_customer` อัตโนมัติ
- เสมียนบันทึกการส่งคืนเล่มทะเบียนจริง (วันที่ส่งคืน, ผู้รับ)

**REQ-STA-006: Contract Default → ยึดรถ** `[GAP FILL]`
- เมื่อ Admin เปลี่ยนสัญญาเป็น `defaulted`:
  - สถานะรถเปลี่ยนกลับเป็น `in_stock` (ยึดรถคืน)
  - customer_id ของรถถูกลบ
  - เล่มทะเบียนยังคงอยู่ที่ร้าน
  - ต้องบันทึกเหตุผลการ default และผู้อนุมัติ

## 5. งานซ่อมบำรุง (Repair/Service)

**REQ-REP-001: เปิด Job Order**
- ระบบต้องสร้างใบสั่งซ่อม (Job Order) ได้ ประกอบด้วย: เลขที่งาน (job_number), ลูกค้า, ทะเบียนรถ, ยี่ห้อ/รุ่น, ช่างผู้รับผิดชอบ, คำอธิบายอาการ/งานที่ต้องทำ
- เลขที่งานระบบสร้างอัตโนมัติ ไม่ซ้ำกัน

**REQ-REP-002: สถานะงานซ่อม**
- `open` — เปิดงานใหม่ รอดำเนินการ
- `in_progress` — กำลังซ่อม
- `completed` — ซ่อมเสร็จแล้ว
- `cancelled` — ยกเลิก

**REQ-REP-003: เพิ่มอะไหล่ในงานซ่อม**
- เลือกอะไหล่จากสต็อก (ค้นหาด้วยชื่อหรือ barcode) ระบุจำนวน
- ต้องตรวจสอบว่าสต็อกเพียงพอก่อนเพิ่ม — ถ้าไม่พอ แจ้งเตือน
- ระบบตัดสต็อกอัตโนมัติทันทีที่เพิ่มอะไหล่ (REQ-INV-004)
- แสดงราคาต่อหน่วย (ราคาขาย) และราคารวม

**REQ-REP-004: บันทึกค่าแรง**
- งานซ่อมต้องบันทึกรายการค่าแรง (labor) แยกจากค่าอะไหล่
- แต่ละรายการค่าแรงมี: คำอธิบาย, ราคา
- ค่าแรงไม่ตัดสต็อก

**REQ-REP-005: คำนวณราคารวมอัตโนมัติ**
- `total_parts_cost = SUM(repair_job_parts.total_price)`
- `total_labor_cost = SUM(repair_job_services.labor_cost)`
- `total_amount = total_parts_cost + total_labor_cost`
- อัปเดตอัตโนมัติทุกครั้งที่เพิ่ม/ลบอะไหล่หรือค่าแรง

**REQ-REP-006: สถานะการชำระเงินงานซ่อม**
- `unpaid` — ยังไม่ชำระ
- `paid` — ชำระครบ
- `partial` — ชำระบางส่วน
- ต้องบันทึก paid_amount ว่าจ่ายไปเท่าไหร่แล้ว

**REQ-REP-007: ปิดงานซ่อม**
- เปลี่ยนสถานะเป็น `completed` ต้องบันทึก completed_at
- ไม่บังคับว่าต้องชำระเงินก่อนปิดงาน (รองรับกรณีลูกค้าเชื่อ)

**REQ-REP-008: งานซ่อมไม่จำเป็นต้องมีลูกค้าในระบบ**
- ลูกค้า walk-in สามารถเข้าซ่อมได้โดยไม่ต้องเป็นลูกค้าในระบบ (customer_id เป็น optional)
- แต่ต้องมีทะเบียนรถเสมอ

**REQ-REP-009: ช่างดูงานเฉพาะที่ได้รับมอบหมาย**
- Technician ดูและจัดการได้เฉพาะงานที่ตัวเองเป็น technician_id

**REQ-REP-010: พิมพ์ใบเสร็จงานซ่อม**
- รองรับพิมพ์ใบเสร็จเมื่อลูกค้าชำระเงิน
- ใบเสร็จแสดง: รายการอะไหล่ทั้งหมด, รายการค่าแรง, ราคารวม

**REQ-REP-011: บันทึก Cash Transaction จากงานซ่อม**
- เมื่อรับชำระเงินงานซ่อม ต้องสร้าง Cash Transaction ประเภท `income` หมวด `repair`

**REQ-REP-012: แนบรูปงานซ่อม**
- รองรับการแนบรูปถ่ายก่อน/หลังซ่อม ในงานแต่ละ Job
- ไม่บังคับ (optional)

## 6. คลังอะไหล่ (Inventory)

**REQ-INV-001: รับอะไหล่เข้าสต็อก (Stock In)**
- บันทึกการรับอะไหล่เข้าสต็อกได้ ระบุ: อะไหล่, จำนวน, ราคาทุนต่อหน่วย
- เพิ่ม quantity_in_stock อัตโนมัติ
- บันทึก stock_movement ประเภท `in`

**REQ-INV-002: เบิกอะไหล่/ขายออก (Stock Out)**
- บันทึกการเบิกอะไหล่ออกจากสต็อก ระบุ: อะไหล่, จำนวน, เหตุผล (repair/sale/adjustment)
- ลด quantity_in_stock อัตโนมัติ
- ต้องตรวจสอบว่าสต็อกเพียงพอ — ถ้าไม่พอ ปฏิเสธ
- บันทึก stock_movement ประเภท `out`

**REQ-INV-003: Barcode Scanner**
- รองรับ USB Barcode Scanner สำหรับรับเข้า/เบิกออกอะไหล่
- Scanner ทำงานเป็น keyboard emulation — Web App รับ input ได้เลย
- เมื่อสแกน barcode ระบบค้นหาอะไหล่ที่ตรงกัน แสดงข้อมูล (ชื่อ, ราคา, สต็อก)

**REQ-INV-004: ตัดสต็อกอัตโนมัติจากงานซ่อม**
- เมื่อเพิ่มอะไหล่ในงานซ่อม ระบบตัดสต็อกทันที (ภายใน transaction เดียวกัน)
- บันทึก stock_movement โดยอ้างอิง job_id

**REQ-INV-005: ขายอะไหล่ปลีก**
- รองรับการขายอะไหล่โดยไม่ผ่านงานซ่อม (ลูกค้าซื้ออะไหล่อย่างเดียว)
- ตัดสต็อกและบันทึก Cash Transaction หมวด `parts`

**REQ-INV-006: ตรวจสอบจำนวนคงเหลือ (Stock Balance)**
- แสดงจำนวนคงเหลือของอะไหล่แต่ละตัวได้
- ค้นหาได้ด้วย: ชื่อ, barcode, part_code, หมวดหมู่

**REQ-INV-007: ประวัติการเคลื่อนไหว (Stock Movement History)**
- ดูประวัติเข้า-ออกของอะไหล่แต่ละตัวได้
- แต่ละ movement บันทึก: วันที่, ประเภท (in/out), จำนวน, ที่มา (reference_type + reference_id), ผู้ดำเนินการ

**REQ-INV-008: แจ้งเตือนสต็อกต่ำ**
- เมื่อ quantity_in_stock ≤ min_stock_level ระบบแจ้งเตือน
- แจ้งเตือนแสดงบนหน้า Dashboard (เสมียน/Owner)

**REQ-INV-009: ปรับสต็อก (Stock Adjustment)**
- รองรับการปรับสต็อกด้วยมือ กรณีนับจริงแล้วไม่ตรง
- ต้องระบุเหตุผลและผู้ดำเนินการ
- บันทึก stock_movement ประเภท `adjustment`

**REQ-INV-010: ตรวจนับสต็อก (Stock Audit)** `[GAP FILL]`
- รองรับการตรวจนับสต็อก (physical count) เป็นระยะ
- ระบบเปรียบเทียบยอดนับจริง vs ยอดในระบบ แสดงส่วนต่าง
- ปรับสต็อกตาม REQ-INV-009 หลังตรวจนับ

## 7. บริการ พ.ร.บ./ภาษี (Insurance & Tax)

**REQ-TAX-001: บันทึกรายการบริการ**
- บันทึกรายการทำ พ.ร.บ. / ต่อภาษีรถได้ ระบุ: ลูกค้า, ทะเบียนรถ, ประเภทบริการ (พ.ร.บ./ภาษี/ทั้งสอง), วันที่ทำ, วันหมดอายุ, ค่าธรรมเนียม (fee_amount), ค่าบริการ (service_charge), ยอดรวม

**REQ-TAX-002: รองรับทั้งชำระทันทีและค้างชำระ**
- สถานะการชำระ: paid, unpaid, partial
- กรณีค้างชำระต้องบันทึกยอดค้าง

**REQ-TAX-003: การจัดการเอกสารทะเบียน**
- ลูกค้าผ่อนชำระ → เล่มทะเบียนอยู่ที่ร้านอยู่แล้ว (registration_source = `shop_held`)
- ลูกค้าทั่วไป → รับเล่มทะเบียนจากลูกค้า (registration_source = `customer_provided`)
- ต้องบันทึกประเภทเอกสารที่รับ: ตัวจริง (original) หรือ สำเนา (copy)

**REQ-TAX-004: สถานะเอกสาร**
- `received` — รับเอกสารแล้ว
- `processing` — กำลังดำเนินการ
- `completed` — ดำเนินการเสร็จ
- `returned` — คืนเอกสารให้ลูกค้าแล้ว

**REQ-TAX-005: บันทึก Cash Transaction**
- เมื่อรับชำระเงินค่า พ.ร.บ./ภาษี ต้องสร้าง Cash Transaction หมวด `insurance_tax`

**REQ-TAX-006: แจ้งเตือน พ.ร.บ./ภาษี ใกล้หมดอายุ**
- ระบบแจ้งเตือนล่วงหน้า 30 วัน ก่อน พ.ร.บ. หรือภาษีรถหมดอายุ
- แจ้งเตือนแสดงบน Dashboard

**REQ-TAX-007: ค่าธรรมเนียมและค่าบริการ**
- ค่าธรรมเนียม (fee_amount) = ค่าที่ต้องจ่ายให้หน่วยงานรัฐ
- ค่าบริการ (service_charge) = ค่าที่ร้านเก็บจากลูกค้าสำหรับบริการ
- ยอดรวม = fee_amount + service_charge

**REQ-TAX-008: ค้นหาประวัติ**
- ค้นหาประวัติบริการ พ.ร.บ./ภาษีได้ด้วย: ทะเบียนรถ, ชื่อลูกค้า, วันที่ทำ

## 8. เงินสดประจำวัน (Daily Cash)

**REQ-CASH-001: เปิดรอบเงินสดประจำวัน**
- ต้องเปิดรอบเงินสดทุกเช้าก่อนเริ่มทำธุรกรรม
- กำหนดยอดเงินสดเริ่มต้น (opening_balance) — เป็นจำนวนเงินสดจริงที่มีในลิ้นชัก
- วันหนึ่งเปิดได้ 1 รอบเท่านั้น (unique per date)

**REQ-CASH-002: บันทึกรายรับ**
- บันทึกรายรับ ระบุ: ประเภท (income), หมวดหมู่, จำนวนเงิน, คำอธิบาย
- หมวดหมู่รายรับ: installment (ค่างวด), repair (ค่าซ่อม), parts (ค่าอะไหล่), insurance_tax (พ.ร.บ./ภาษี), vehicle_sale (ขายรถ), theft_insurance (ประกันรถหาย), other
- ส่วนใหญ่สร้างอัตโนมัติจาก Module อื่น (ค่างวด, ค่าซ่อม, ค่าอะไหล่) — เสมียนไม่ต้องบันทึกซ้ำ

**REQ-CASH-003: บันทึกรายจ่าย**
- บันทึกรายจ่าย ระบุ: ประเภท (expense), หมวดหมู่, จำนวนเงิน, คำอธิบาย
- หมวดหมู่รายจ่าย: petty_cash (เงินสดย่อย), supplier (จ่ายซัพพลายเออร์), other
- ตัวอย่าง: ช่างเบิกเงินซื้อของ, ค่าเดินทาง, ค่าใช้จ่ายทั่วไป

**REQ-CASH-004: ปิดรอบเงินสดประจำวัน**
- ปิดรอบเงินสดตอนปิดร้าน
- ระบบคำนวณ: `closing_balance = opening_balance + total_income - total_expense`
- ต้องเปรียบเทียบยอดจริง (นับเงินในลิ้นชัก) กับยอดในระบบ
- ถ้ายอดไม่ตรง ต้องบันทึกเหตุผล

**REQ-CASH-005: สรุปรายรับ-รายจ่ายแยกตามหมวด**
- ระบบต้องสรุปรายรับ-รายจ่ายแยกตามหมวดหมู่ได้
- แสดงทั้งยอดรวมและรายละเอียดแต่ละรายการ

**REQ-CASH-006: ต้องเปิดรอบก่อนบันทึกธุรกรรม**
- ถ้ายังไม่เปิดรอบเงินสดวันนั้น การบันทึกรายรับ/รายจ่ายจะทำไม่ได้
- ระบบแจ้งให้เปิดรอบก่อน

**REQ-CASH-007: Auto-link จาก Module อื่น**
- เมื่อรับชำระเงินจาก Module ใดก็ตาม (ค่างวด, งานซ่อม, อะไหล่, พ.ร.บ., ขายรถ) ระบบต้องสร้าง Cash Transaction อัตโนมัติ
- เสมียนไม่ต้องไปบันทึกในหน้า Cash แยก — ลดขั้นตอนและป้องกันการลืม
- Cash Transaction ต้อง reference_type + reference_id กลับไปที่ธุรกรรมต้นทาง

**REQ-CASH-008: ยอดเงินสดคงเหลือ Real-time**
- ระบบต้องแสดงยอดเงินสดคงเหลือปัจจุบันได้ตลอดเวลา (opening + income - expense)

**REQ-CASH-009: ส่งสรุปให้เจ้าของร้าน**
- สรุปรายรับ-รายจ่ายประจำวัน ต้องส่งให้เจ้าของร้านดูได้ (ผ่าน Dashboard/Push Notification)

**REQ-CASH-010: ห้ามลบ/แก้ไข Transaction**
- Cash Transaction ที่บันทึกแล้วจะลบหรือแก้ไขไม่ได้
- แก้ไขได้ด้วย reversal entry (บันทึกรายการกลับรายการ) เท่านั้น

**REQ-CASH-011: บันทึกเงินจาก Collector**
- เมื่อ Collector ส่งเงินกลับร้านและเสมียนตรวจรับ ต้องสร้าง Cash Transaction หมวด `installment` อัตโนมัติ

## 9. ติดตามหนี้ (Collection)

**REQ-COL-001: รายชื่อลูกหนี้ค้างชำระ**
- ระบบแสดงรายชื่อลูกค้าที่ค้างชำระค่างวด ประกอบด้วย: ชื่อลูกค้า, เลขสัญญา, จำนวนงวดที่ค้าง, ยอดเงินค้าง, จำนวนวันที่ค้าง (Aging)

**REQ-COL-002: มอบหมายงานติดตาม**
- เสมียน/Admin เลือกลูกหนี้จากรายชื่อ แล้วมอบหมายให้ Collector
- ข้อมูลที่ส่งให้ Collector: ลูกค้า (ชื่อ, ที่อยู่, เบอร์โทร, รูปลูกค้า), สัญญา, ยอดค้าง, ข้อมูลผู้ค้ำประกัน (ถ้ามี), ลำดับความสำคัญ (priority)
- 1 สัญญาจะมีงานติดตามที่เปิดอยู่ได้แค่ 1 งานในเวลาเดียวกัน

**REQ-COL-003: ลำดับความสำคัญ (Priority)**
- งานติดตามมี priority: 0 = ปกติ, 1 = ด่วน, 2 = ด่วนมาก
- แสดงบน Mobile App ของ Collector เรียงตาม priority

**REQ-COL-004: Collector ดูงานบน Mobile**
- Collector เห็นรายการงานที่ได้รับมอบหมาย บน Mobile App
- แต่ละงานแสดง: ชื่อลูกค้า, ที่อยู่, เบอร์โทร, ยอดค้าง, priority
- กดโทรหาลูกค้าได้ 1 แตะ
- เปิด Google Maps นำทางไปบ้านลูกค้าได้ 1 แตะ

**REQ-COL-005: Collector ดูประวัติลูกค้า**
- Collector ดูข้อมูลได้: สัญญา, รถที่ซื้อ, ข้อมูลผู้ค้ำประกัน, รูปลูกค้า, ประวัติการติดตามก่อนหน้า
- Collector ไม่มีสิทธิ์แก้ไขข้อมูลใดๆ ของลูกค้า/สัญญา/งวด — ทำได้แค่ "ดู" + "บันทึกผลติดตาม" + "รับเงิน"

**REQ-COL-006: บันทึกผลการติดตาม**
- Collector บันทึกผลได้ 7 แบบ:
  1. `contacted_promise_to_pay` — ติดต่อได้ นัดจ่าย (ต้องระบุวันนัด)
  2. `contacted_cannot_pay` — ติดต่อได้ แต่จ่ายไม่ได้
  3. `not_home` — ไม่อยู่บ้าน
  4. `unreachable` — ติดต่อไม่ได้
  5. `paid_on_site` — จ่ายเงินครบหน้างาน
  6. `partial_paid_on_site` — จ่ายบางส่วนหน้างาน
  7. `other` — อื่นๆ (ต้องระบุหมายเหตุ)

**REQ-COL-007: รับเงินหน้างาน (Field Payment)**
- Collector สามารถรับเงินสดจากลูกค้าได้หน้างาน
- ต้องระบุยอดเงินที่เก็บ
- ระบบออกใบเสร็จชั่วคราว (Field Receipt) ให้ลูกค้าทันที (PDF)
- สถานะเงิน: `collected` (เก็บเงินแล้ว ยังไม่ส่งร้าน)

**REQ-COL-008: GPS Log**
- ระบบบันทึกตำแหน่ง GPS อัตโนมัติเมื่อ Collector บันทึกผลการติดตาม
- เป็นหลักฐานว่า Collector ออกพื้นที่จริง
- ต้องแจ้ง Collector ว่า GPS ถูก log ขณะปฏิบัติงาน (PDPA)
- ไม่ log GPS นอกเวลางาน

**REQ-COL-009: ส่งเงินกลับร้าน**
- Collector กลับร้าน → ส่งเงินให้เสมียน
- เสมียนตรวจรับเงิน ยืนยันยอด
- สถานะเงินเปลี่ยน: `collected` → `submitted` → `verified`
- เมื่อ `verified`: ระบบบันทึก Cash Transaction + อัปเดตงวดที่จ่าย (เหมือนรับเงินที่ร้าน)

**REQ-COL-010: เงิน Collector vs ยอดในระบบ**
- ยอดที่ Collector รับต้องตรงกับยอดใน contract ± tolerance เล็กน้อย
- ถ้ายอดไม่ตรง ต้องมีหมายเหตุ

**REQ-COL-011: สถานะงานติดตาม**
- `assigned` — มอบหมายแล้ว ยังไม่เริ่ม
- `in_progress` — กำลังดำเนินการ (เมื่อ Collector บันทึกผลครั้งแรก)
- `completed` — เสร็จสิ้น (ลูกค้าจ่ายแล้ว หรือ Admin ปิดงาน)
- `cancelled` — ยกเลิก

**REQ-COL-012: Offline Support**
- Collector อาจอยู่ในพื้นที่ไม่มี Internet
- ระบบต้องรองรับบันทึกข้อมูลลง Local Storage ก่อน → Sync เมื่อมี Internet (Offline-first)
- ข้อมูลที่ต้อง cache: รายชื่อลูกหนี้, ประวัติลูกค้า, รูปลูกค้า

**REQ-COL-013: Push Notification สำหรับ Collector**
- แจ้ง Collector เมื่อได้รับงานใหม่
- แจ้ง Collector เมื่องานถูกเปลี่ยนแปลง (เช่น ลูกค้ามาจ่ายที่ร้านแล้ว)

**REQ-COL-014: สรุปประจำวันของ Collector**
- Collector ดูสรุปงานวันนี้ได้: ติดตามแล้วกี่ราย, เก็บเงินได้เท่าไหร่, ยังไม่ส่งร้านเท่าไหร่

**REQ-COL-015: ใบเสร็จชั่วคราว (Field Receipt)**
- ใบเสร็จชั่วคราวมีเลขที่แยกจากใบเสร็จร้าน (field_receipt_number)
- แสดงข้อมูล: ลูกค้า, สัญญา, ยอดที่เก็บ, วันที่, ชื่อ Collector
- พิมพ์เป็น PDF แสดงบนมือถือ (ลูกค้าดูจากจอหรือ share ได้)

**REQ-COL-016: รายงานติดตามหนี้**
- รายงานสรุปผลติดตาม: จำนวนงานที่มอบหมาย, ผลลัพธ์ (จ่ายกี่ราย, นัดจ่ายกี่ราย, ติดต่อไม่ได้กี่ราย)
- รายงานเงินที่เก็บได้: ยอดรวม, แยกตาม Collector
- แสดงให้ Admin/Clerk ดู

## 10. รายงาน/แดชบอร์ด (Reports & Dashboard)

**REQ-RPT-001: สรุปรายวัน (Daily Summary)**
- รายรับ-รายจ่ายแยกตามหมวดหมู่, ยอดเงินสดคงเหลือ
- ส่งให้เจ้าของร้านดูได้ทุกวัน (ผ่าน Dashboard / Push Notification)

**REQ-RPT-002: รายงานการขาย (Sales Report)**
- ยอดขายรถ รายสัปดาห์/เดือน
- แยกตามประเภท (เงินสด/ผ่อน), ยี่ห้อ, สภาพ (ใหม่/มือสอง)

**REQ-RPT-003: รายงานลูกหนี้ (Receivable Report)**
- รายชื่อลูกค้าค้างชำระ, จำนวนเงินค้าง, จำนวนงวดที่ค้าง
- เรียงตามจำนวนวันที่ค้าง (Aging: 1-30 วัน, 31-60 วัน, 61-90 วัน, >90 วัน)

**REQ-RPT-004: Aging Report (Collection)**
- ลูกค้าที่เกินกำหนดชำระ เรียงตามจำนวนวันที่ค้าง
- แสดงสถานะการติดตาม (มอบหมาย Collector แล้ว/ยัง)

**REQ-RPT-005: รายงานงานซ่อม (Repair Report)**
- สรุปงานซ่อมรายวัน/เดือน, รายได้จากงานซ่อม (ค่าอะไหล่ + ค่าแรง)

**REQ-RPT-006: รายงานสต็อกอะไหล่ (Inventory Report)**
- รายงานสต็อกคงเหลือ, สินค้าขายดี, สินค้าค้างสต็อก
- รายการที่ต่ำกว่า min_stock_level

**REQ-RPT-007: Export รายงาน**
- รองรับ Export รายงานเป็น PDF และ Excel

**REQ-RPT-008: รายงานกองกลางประกันรถหาย** `[GAP FILL]`
- ยอดเงินกองกลางปัจจุบัน
- รายการเงินเข้า/ออก
- สถิติ: จำนวนสัญญาที่มีประกัน, จำนวนเคสรถหาย
- (ดูรายละเอียด REQ-INS-013)

**REQ-RPT-009: Owner Dashboard**
- แสดงบน Mobile App ของ Owner:
  - รายได้วันนี้ (แยกตามประเภท)
  - แจ้งเตือน: ลูกค้าค้างชำระ, อะไหล่ใกล้หมด, งานซ่อมรอปิด
  - Drill-down: แตะตัวเลขดูรายละเอียดได้
- Owner ไม่ต้องบันทึกข้อมูลใดๆ — เป็น Read-only Dashboard

**REQ-RPT-010: Push Notification สำหรับ Owner**
- แจ้งเตือนเมื่อ: มีค่างวดค้างเกิน X วัน, เปิด/ปิดร้าน, ยอดผิดปกติ, สต็อกต่ำ

**REQ-RPT-011: Clerk Dashboard**
- แสดงบน Web App ของเสมียน:
  - Quick Actions: รับค่างวด, เปิดงานซ่อม, ขายอะไหล่, สร้างสัญญา, พ.ร.บ./ภาษี, เงินสดประจำวัน
  - แจ้งเตือน: ลูกค้าค้างชำระเกิน 30 วัน, อะไหล่ใกล้หมดสต็อก, งานซ่อมรอปิด

**REQ-RPT-012: รายงานติดตามหนี้ (Collection Report)**
- สรุปผลติดตาม, เงินที่เก็บได้, แยกตาม Collector

## 11. Authentication & Authorization

**REQ-AUTH-001: ระบบ Login**
- ผู้ใช้ login ด้วย username + password
- ไม่มีระบบ self-registration — Admin สร้าง user ให้

**REQ-AUTH-002: JWT Authentication**
- ใช้ JWT (JSON Web Token) สำหรับ authentication
- Access token หมดอายุ 24 ชั่วโมง
- Refresh token หมดอายุ 7 วัน
- JWT เก็บใน httpOnly cookie (ป้องกัน XSS) — ไม่ใช้ localStorage

**REQ-AUTH-003: Refresh Token Rotation**
- ทุกครั้งที่ refresh token → ออก token ใหม่ + revoke token เก่า
- ป้องกัน token theft

**REQ-AUTH-004: Login Lockout**
- หลัง login fail 5 ครั้งติดต่อกัน → block 15 นาที
- ป้องกัน brute force

**REQ-AUTH-005: Password Hashing**
- ใช้ Argon2id สำหรับ hash password (OWASP recommendation)

**REQ-AUTH-006: Role-Based Access Control (RBAC)**
- 4 Roles: Admin, Clerk, Technician, Collector
- แต่ละ Role มีสิทธิ์ตามตารางด้านล่าง

**REQ-AUTH-007: Permission Matrix**

| Feature | Owner/Admin | Clerk | Technician | Collector |
|---------|-------------|-------|------------|-----------|
| Dashboard / สรุปรายได้ | ✅ (Mobile) | ✅ (Web) | ❌ | ❌ |
| จัดการลูกค้า | CRUD | CRUD | ❌ | Read-only |
| จัดการรถ / สต็อกรถ | CRUD | CRUD | ❌ | ❌ |
| สร้างสัญญาซื้อขาย | CRUD | CRUD | ❌ | ❌ |
| รับชำระค่างวด (ที่ร้าน) | ❌ | CRUD | ❌ | ❌ |
| งานซ่อม | Read-only | เปิด/ปิด Job | CRUD (งานตัวเอง) | ❌ |
| อะไหล่ / สต็อก | Read-only | CRUD | เบิกอะไหล่ (Barcode) | ❌ |
| เงินสดประจำวัน | Read-only | CRUD | ❌ | ❌ |
| พ.ร.บ. / ภาษี | Read-only | CRUD | ❌ | ❌ |

**REQ-AUTH-008: Audit Log**
- ทุก action สำคัญต้องบันทึก Audit Log: user, action, table, record_id, old_values, new_values, IP address, timestamp
- Action สำคัญ: สร้าง/แก้ไข/ลบสัญญา, รับชำระเงิน, เปลี่ยนสถานะสัญญา, ยกเว้นค่าปรับ, อนุมัติรถหาย, ลบข้อมูล

## 12. Security & Privacy

**REQ-SEC-001: HTTPS Only**
- ทุก communication ต้องใช้ HTTPS (TLS 1.3)
- ห้ามใช้ HTTP

**REQ-SEC-002: Input Validation**
- ทุก endpoint ต้องมี input validation (Zod schema)
- ป้องกัน SQL Injection ด้วย parameterized queries (ORM)

**REQ-SEC-003: CORS**
- CORS whitelist เฉพาะ domain ของร้าน — ไม่ใช้ `*`

**REQ-SEC-004: CSP Header**
- ใช้ Content-Security-Policy ป้องกัน XSS ใน browser

**REQ-SEC-005: CSRF Protection**
- ใช้ SameSite=Strict cookie + Origin header check

**REQ-SEC-006: XSS Prevention**
- React escape HTML by default
- ห้ามใช้ `dangerouslySetInnerHTML` กับ user input โดยไม่ sanitize

**REQ-SEC-007: Financial Transaction Integrity**
- ทุก payment ใช้ database transaction (atomic) — ป้องกันเงินหาย/ข้อมูลไม่สอดคล้อง
- ทุก POST payment ส่ง Idempotency Key ป้องกัน double charge จาก retry
- Payment records ลบไม่ได้ — แก้ไขด้วย reversal entry เท่านั้น

**REQ-SEC-008: Soft Delete**
- ข้อมูลสำคัญทุกตารางใช้ Soft Delete เท่านั้น (ไม่ลบจริง)
- บันทึก deleted_at, deleted_by

**REQ-SEC-009: Database Backup**
- Backup อัตโนมัติทุกวัน
- Backup encrypt ก่อน upload ไปยัง offsite storage

**REQ-SEC-010: Rate Limiting**
- Rate limit สำหรับ login attempts
- Rate limit สำหรับ API endpoints ทั่วไป

**REQ-SEC-011: PDPA Compliance**
- ระบบเก็บข้อมูลส่วนบุคคล (PII) → ต้องมี consent + purpose limitation
- GPS Collector: แจ้งว่า GPS ถูก log ขณะปฏิบัติงาน — ไม่ log นอกเวลางาน
- Data Retention: ลูกค้าปิดสัญญา → archive ข้อมูล 5 ปี ตาม พ.ร.บ.บัญชี → ลบ
- รูปถ่ายลูกค้า: ต้องได้รับความยินยอมก่อนถ่าย (REQ-PHO-009)

**REQ-SEC-012: Secrets Management**
- ไม่ commit .env หรือ credentials ลง repository
- Production ใช้ environment variables
- SSH key only (ไม่ใช้ password) สำหรับ VPS access

## 13. Hardware

**REQ-HW-001: Barcode Scanner (USB)**
- รองรับ USB Barcode Scanner ที่ทำงานเป็น keyboard emulation (HID)
- ไม่ต้องติดตั้ง driver พิเศษ — Web App รับ input ได้ทันที
- แยกแยะ scanner (keystroke < 30ms) กับคนพิมพ์ (keystroke > 100ms)

**REQ-HW-002: Thermal Printer (80mm)**
- รองรับ thermal printer 80mm ผ่าน USB
- พิมพ์ใบเสร็จทันที ไม่มี print dialog
- ตัดกระดาษอัตโนมัติ
- ใช้ ESC/POS protocol

**REQ-HW-003: กล้อง (Camera)**
- รองรับถ่ายรูปจาก webcam (PC) หรือกล้องมือถือ (Mobile)
- ใช้สำหรับถ่ายรูปลูกค้า (REQ-PHO) และแนบรูปงานซ่อม (REQ-REP-012)

**REQ-HW-004: GPS**
- รองรับ GPS บน Mobile App สำหรับ Collector
- ใช้สำหรับ REQ-COL-008

## 14. Multi-Platform

**REQ-PLT-001: Shared Backend**
- ทุก Platform ใช้ Backend API เดียวกัน (REST)
- ข้อมูลสอดคล้องกัน real-time

**REQ-PLT-002: Web App (เสมียน + ช่าง)**
- ใช้บน PC จอใหญ่
- รองรับ Barcode Scanner, Thermal Printer
- Sidebar navigation เห็น Menu ตลอด
- Keyboard Shortcut สำหรับ Quick Actions

**REQ-PLT-003: Mobile App (เจ้าของร้าน)**
- Dashboard สรุปรายวัน
- ดูรายงาน
- Push Notification
- Read-only (ไม่ต้องบันทึกข้อมูล)

**REQ-PLT-004: Mobile App (Collector)**
- ดูงานติดตาม
- บันทึกผลติดตาม
- รับเงินหน้างาน + ออกใบเสร็จชั่วคราว
- GPS tracking
- Offline support
- Push Notification

**REQ-PLT-005: UX หลักการ**
- Less is More: แต่ละหน้าจอมีจุดประสงค์เดียว
- Big Touch Targets: ปุ่มใหญ่ ข้อความใหญ่ โดยเฉพาะ Mobile (min 44px)
- Minimal Typing: ใช้ Dropdown, Quick Select, Barcode แทนพิมพ์
- Instant Feedback: ทุก action มี success/error feedback
- Forgiving Design: ยืนยันก่อนลบ, Undo ได้เมื่อเป็นไปได้

**REQ-PLT-006: ขนาดตัวอักษรขั้นต่ำ**
- Web: 14px
- Mobile: 16px
- ตัวเลขเงิน: Tabular nums, font-weight 600

**REQ-PLT-007: รองรับภาษาไทย**
- UI ทั้งหมดเป็นภาษาไทยเป็นหลัก
- Font รองรับภาษาไทย (Inter / Sarabun สำหรับ Web, System font สำหรับ Mobile)
- จำนวนเงินแสดงในรูปแบบไทย (เช่น 2,500.00 บาท)

## 15. ข้อจำกัดและสมมติฐาน (Constraints & Assumptions)

**REQ-CON-001: Solo Developer**
- ระบบพัฒนาโดย Solo Developer ที่ใช้ AI-assisted coding (Claude Code)
- ไม่ต้องลดความซับซ้อนเพราะกำลังคน

**REQ-CON-002: SME Scale**
- ระบบออกแบบสำหรับร้านเดียว ไม่ต้องรองรับ multi-branch
- จำนวนผู้ใช้พร้อมกัน: 5-10 คน

**REQ-CON-003: Internet Dependency**
- ระบบต้องการ Internet สำหรับทำงาน (Cloud-hosted)
- Offline support มีสำหรับ Collector เท่านั้น (Local cache → Sync)
- หาก Internet ดับ ให้ deploy local server เป็น fallback

**REQ-CON-004: ไม่ใช่ระบบบัญชี (Accounting)**
- ระบบนี้ไม่ใช่ระบบบัญชี (accounting software)
- จัดการเงินสดเข้า-ออกเท่านั้น ไม่มี double-entry bookkeeping

**REQ-CON-005: สกุลเงินเดียว**
- รองรับเฉพาะสกุลเงินบาท (THB) เท่านั้น

**REQ-CON-006: เวลาทำการ**
- ระบบทำงาน 24/7 แต่ธุรกรรมหลัก (เปิด/ปิดเงินสด, รับชำระ) เกิดในเวลาทำการร้าน
- Scheduled Jobs (คำนวณค่าปรับ, แจ้งเตือน) ทำงานอัตโนมัตินอกเวลาทำการ
